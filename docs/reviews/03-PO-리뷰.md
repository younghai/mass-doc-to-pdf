## 제품 한 줄 정의 + 현재 단계 진단

**한 줄 정의(실제 코드 기준):** "HWP/HWPX/Office 문서를 업로드하면 엔진 체인으로 PDF 변환하고, 성공/실패/저품질(review)을 분리해 운영자가 검수·재시도할 수 있게 하는 대량 문서 변환 운영 도구."

**현재 단계: 잘 만들어진 내부 운영 도구(internal tool) — 외부 공개 서비스로는 미성숙.**

- **핵심 변환 파이프라인은 실장(shipped) 상태.** `Upload.tsx`, `BatchUpload.tsx`(최대 1,000개, `MAX_BATCH_FILES=1000`), `Jobs.tsx`, `JobDetail.tsx`(품질 리포트 + PDF/PNG 미리보기 + 재시도)가 실제 API에 연결돼 있고 use-case 문서(UC-01~10)와 일치한다.
- **문서화 성숙도는 높으나(waterfall 00~11 전 단계) 제품-시장 정합성은 낮다.** 기획서(`service-planning.md`)는 타겟을 "공공기관 담당자 / 기업 운영팀 / 개발자"로 명시하지만, 랜딩·로그인·대시보드가 이 타겟·차별점을 반영하지 못한다.
- **가장 큰 리스크는 미커밋 Meetings WIP.** 설계 문서는 완전한 백엔드(`/api/meetings`, Prisma `Meeting` 모델, 큐 워커, 동의 게이트, 접근 제어)를 명시하지만, 실제 구현은 **localStorage 전용 클라이언트 목업**이며 백엔드가 전혀 없다. 그런데도 주 내비게이션에 "회의록"으로 정식 노출된다.

**배포 가능 여부: 조건부 가능(내부/신뢰 호스트 한정) / 외부 일반 공개 불가.** 차단 항목은 P0 3건(Meetings 목업의 프로덕션 노출, 법적 고지 부재, 가치 제안 전달 실패).

## Meetings WIP 전략 평가

**판정: 현 상태로는 스코프 크리프(scope creep)에 가깝다.** 전략적 확장으로 전환할 논리적 근거는 존재하나, 문서로 입증되지 않았고 실행 상태가 위험하다.

- **근거 1 — 비전 문서에 근거 없음.** `service-planning.md`·`business-policy.md`·README 어디에도 회의록/음성 전사가 로드맵·타겟·가치 제안으로 없다. README "향후 고도화"(313~318)는 전부 변환 품질 고도화(raster, Hancom SDK, 배치 리포트, 자동 품질 지표, 검수 UI)다.
- **근거 2 — 전략적 정합성의 *잠재적* 근거는 있음.** 타겟이 "공공기관/기업 운영팀"이라면 회의록→PDF 내보내기는 인접 워크플로우다. 설계도 "기존 Fastify/Prisma/queue 패턴 재사용"을 명시한다. "문서 운영 플랫폼"으로 포지션을 넓히는 서사는 성립 가능하나 비전 문서에 반영되지 않았다.
- **근거 3 — 우선순위 역전.** README 향후 고도화의 핵심(검수 UI: 담당자/메모/증거 — 차별점 완성)이 미구현인데, 로드맵에 없는 Meetings가 먼저 UI 표면(주 nav)에 올라왔다.
- **근거 4 — 실행이 설계 대비 심각 미달.** 설계는 성숙(상태머신·접근제어·동의·adapter·테스트 계획)한데 구현은 localStorage 목업이다. 설계와 구현이 다른 속도로 진행돼 문서 신뢰도까지 훼손한다.

**권장 결정 프레임:**
- **정식 승격 시** → 먼저 `service-planning.md`에 "문서 운영 플랫폼" 비전·회의록 타겟/KPI 추가 → 핵심 차별점(검수 UI) P0 완성 → Meetings 백엔드를 설계대로 구현. 그 전까지 nav에서 제거.
- **탐색/데모라면** → 주 nav에서 즉시 제거하거나 `/labs` 격리 + 외부 배포 빌드에서 제외.
